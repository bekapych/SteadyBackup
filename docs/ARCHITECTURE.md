# SteadyBackup — архитектура

Гибрид Cobian Reflector (задания, планировщик, типы копий, служба) и Effector Saver
(1С, MSSQL, облака, простота).

## Компоненты

```
┌──────────────────────┐   Named Pipe \\.\pipe\SteadyBackup   ┌──────────────────────────┐
│  steady-gui (Qt6)    │ ◄──────── JSON-RPC (строки) ───────► │  steady-service (Rust)    │
│  трей, мастер задач, │                                      │  Windows-служба, SYSTEM   │
│  журнал, прогресс    │                                      │  планировщик + движок     │
└──────────────────────┘                                      └────────────┬─────────────┘
                                                                           │
                                                SQLite: задания, история, каталог файлов
```

* Служба работает без GUI. GUI только клиент (QLocalSocket ↔ Named Pipe).
* Пароли и токены хранятся через DPAPI (LocalMachine) и никогда не пишутся открытым текстом.

## Конвейер задания

```
 [pre-события] → Источник → staging-каталог → 7-Zip (+пароль) → Назначения (1..N) → Ротация → [post-события] → Отчёт
```

Каждое задание = 1 источник-тип + N назначений. Ошибка одного назначения не отменяет остальные.

Ротация (`retention`): `keep_full` — последние полные цепочки; `keep_days` и `keep_sets`
(`0` — выключено) — наборы без своей полной копии и хвост старше сохранённой полной.
Чужие файлы и `.partial` не удаляются.

Повторы (`util::retry`, пауза 1, 2, 4 … с, не больше минуты; отмена не повторяется):
подготовка источника и упаковка 7-Zip — `Job::step_attempts()` (по умолчанию 1), отправка каждого
тома в каждое назначение — `Job::upload_attempts()` (по умолчанию 5), после ошибки назначение
открывается заново. Перед повтором staging очищается, тома прошлой упаковки удаляются.
После каждой попытки отправки сверяется размер. Несовпадение — ошибка, объект отправляется заново через `.partial`.
Поле задания `attempts` (>0) задаёт оба числа. MS SQL и PostgreSQL повторяют каждую базу
отдельно (`Source::retries_per_item`): неудачная база не мешает остальным, они отправляются,
а запуск после отправки завершается ошибкой (`Prepared::failures`).

Несколько баз в отдельных архивах (`separate_archives`): источник возвращает `Prepared::parts`,
конвейер раскладывает файлы по `run_dir\parts\<метка>` и пакует каждую часть в
`<набор>.<метка>.7z`. `parse_set` берёт ключ набора до точки после вида, поэтому ротация
удаляет архивы одного запуска вместе.

Перезапуск задания (`restarts`, `restart_delay_minutes`): после ошибочного запуска (не отмены) движок
кладёт задание в список ожидания в памяти и ставит в очередь по истечении паузы; каждый запуск —
отдельная запись журнала, уведомление — только по последнему. Отмена снимает ждущий перезапуск,
остановка службы сбрасывает их. Запуск по расписанию группы подставляет ненулевые
`restarts`/`restart_delay_minutes`/`attempts` группы (`group::RetryOverride`).

Остановка службы выставляет флаг отмены, дожидается исполнителя до 30 с (`StopPending`) и завершает
дочерние процессы. `cancel_job` делает то же для одного задания.

Группы заданий (`group.rs`, `<data>\groups\`, метки — `group-marks.json`): своё расписание, по которому
включённые задания группы ставятся в общую очередь по порядку группы. Задание — не больше чем в одной
группе (`Job::group`), его собственное расписание тоже действует. Метки групп подчиняются тем же
правилам, что метки заданий (сброс при правке расписания, отключённые не хранят метку).

Рабочий каталог (`settings.json`, поле `work_dir`, по умолчанию `<data>\work`) — staging и архив.
При старте службы из него удаляются только недоделанные каталоги заданий. Перед копированием файла
известного размера и перед упаковкой проверяется свободное место.

Если инкрементная или дифференциальная копия дошла не до всех назначений, в состоянии
ставится `force_full`: следующая копия полная (файлы, Hyper-V, MSSQL), иначе в отставшем
назначении остаётся дыра в цепочке. Поле с `#[serde(default)]`, старые `state\*.json` читаются.

## Источники

| Тип | Как делаем | Режимы |
|---|---|---|
| **1С файловая база** | Средствами платформы: `1cv8.exe DESIGNER /F"<каталог>" /N /P /DumpIB "<file>.dt" /Out log /DisableStartupDialogs`. Перед выгрузкой проверка/блокировка сеансов (опция «завершить сеансы» через `/UC` + код блокировки). Альтернативный режим: копия `1Cv8.1CD` через VSS (быстро, без остановки работы). Проверка результата: код возврата + разбор лог-файла. | Полная |
| **MSSQL** | T-SQL через `tiberius` (сейчас временно через `sqlcmd`): `BACKUP DATABASE … TO DISK … WITH COMPRESSION, CHECKSUM`, `BACKUP LOG`. Опционально `RESTORE VERIFYONLY`. Файл .bak создаёт сам SQL Server (на своей машине) → дальше забираем по пути/UNC. | Полная / Дифф. / Журнал |
| **Firebird** | `gbak -b` той же версии, что сервер. Пароль через `ISC_PASSWORD`. Проверка — `gbak -c` во временный файл, в архив попадает `.fbk`. | Полная |
| **PostgreSQL** | `pg_dump -Fc` по каждой базе (`<база>.dump`); пусто — все базы из `pg_database` (через `psql`). Опционально `pg_dumpall --globals-only` → `globals.sql`. Проверка — `pg_restore --list`. Пароль через `PGPASSWORD`; имя базы передаётся как `dbname='…'`. Утилиты из одного каталога `bin`, проверка `acl::check_trusted_exe`. Подключение типа `postgresql` (`host`, `port`, `user`, `password`). | Полная |
| **MySQL по SSH** (`source/mysql.rs`) | Вход по SSH (`ssh.rs`, russh, сжатие zlib), на сервере `sh -c` запускает `mysqldump`/`mariadb-dump --single-transaction --databases <база>`; вывод канала пишется в `<база>.sql`. Учётные данные MySQL — через stdin во временный файл 0600 (`--defaults-extra-file`), имя базы — в одинарных кавычках (`ssh::sh_quote`). Пусто — все базы из `SHOW DATABASES` без системных. Проверка — строка `-- Dump completed`. Повтор каждой базы через новое соединение, `separate_archives`. | Полная |
| **Файлы по SSH** (`source/sshfiles.rs`) | SFTP поверх того же входа: обход каталогов в ширину, скачивание изменённых файлов. Каталог изменений, манифест и правила «удалён / не прочитан» общие с `files.rs` (`Run`, `finish`); mtime SFTP — секунды. | Полная / Инкр. / Дифф. |
| **Файлы** | Локальные, UNC (SMB), WebDAV. Открытые файлы — через VSS (локальные тома). Каталог состояния в SQLite (путь, размер, mtime, опц. хеш BLAKE3). | Полная / Инкр. / Дифф. / Зеркало |
| **Hyper-V** | Production checkpoint (VSS внутри гостя) → копирование VHDX/конфигурации → слияние checkpoint. Через WMI `root\virtualization\v2`. Этап 1: `Export-VM` (просто и надёжно). Этап 2: RCT (Resilient Change Tracking) для инкрементных копий. | Полная (→ Инкр. на RCT) |

### Логика инкрементных/дифференциальных копий файлов
* **Полная**: все файлы; каталог-база := текущий снимок.
* **Дифференциальная**: изменённые относительно последней *полной*.
* **Инкрементная**: изменённые относительно последней *любой* копии.
* Удалённые файлы фиксируются в манифесте набора (`manifest.json` внутри архива) — для корректного восстановления.
* Цепочки: «полная каждые N копий / каждый N-й день», ротация удаляет цепочку целиком.

## Назначения

| Тип | Реализация |
|---|---|
| Локальная папка | std::fs |
| SMB / Samba | UNC-путь + `WNetAddConnection2` с учётными данными задания |
| SFTP | `russh` + `russh-sftp` (чистый Rust), ключ или пароль |
| SSH | Тот же канал + выполнение команд (post-команды на сервере, `scp`-совместимость не нужна) |
| WebDAV | `reqwest`: PUT / MKCOL / PROPFIND / DELETE, Basic/Digest |
| Google Drive | OAuth2 (installed app, loopback-redirect, PKCE), refresh-token в DPAPI; resumable upload API v3 |

Общий трейт: `put(file)`, `list(prefix)`, `delete(path)`, `mkdir`. На нём же построена ротация.

## Упаковка 7-Zip

* В комплекте `7za.exe` (LGPL), запускается процессом: многопоточный LZMA2, AES-256,
  шифрование заголовков `-mhe=on` (скрывает имена файлов), тома `-v<size>`.
* Уровень сжатия, размер тома, пароль задаются в задании.
* Проверка архива `7za t` перед отправкой (опция).

## Планировщик

Однократно, ежедневно, еженедельно (дни недели), ежемесячно, интервал (каждые N минут/часов),
при старте службы. Пропущенные запуски → «выполнить при старте» (опция). Очередь заданий,
лимит параллельных заданий.

## Безопасность

* **Каталог данных** `%ProgramData%\SteadyBackup` — защищённый DACL без наследования:
  только SYSTEM и «Администраторы» (`acl::secure_data_dir`, при каждом старте службы и в `steady install`).
  Служба загружает только задания, владелец файла которых — SYSTEM или «Администраторы».
* **IPC**: читать состояние, список заданий, журнал, хранилища и подключения (с замаскированными
  секретами) может любой вошедший пользователь. Менять задания и настройки, запускать задания —
  только клиент с правами администратора **с повышением UAC** или SYSTEM (олицетворение клиента
  канала + `CheckTokenMembership`). GUI без повышения работает в режиме просмотра и предлагает
  перезапуск через UAC.
* **Список баз** (`list_databases`): окно задания MS SQL / PostgreSQL запрашивает базы сервера
  через выбранное подключение — это же проверка подключения. Служба выполняет `sqlcmd` или `psql`
  (те же проверки путей, пароль через окружение), только для администратора. Для MySQL — `mysql -N -B -e
  'SHOW DATABASES'` на сервере SSH; для «Файлов по SSH» — `check_ssh_paths` (вход и `stat` путей).
* **SSH-источники**: подключение типа `ssh` хранит пароль и пароль ключа в DPAPI (оба маскируются для GUI).
  Отпечаток сервера не закреплён — вход разрешается, а в итог запуска пишется предупреждение с отпечатком.
  Пароль MySQL не попадает в командную строку сервера. Ключи SSH из подключений и заданий переносятся
  экспортом настроек (`key_files`).
* **Обновление** (`steady-core/update.rs`, `steady-service/updater.rs`): выпуски берутся только из
  `github.com/bekapych/SteadyBackup/releases` (ссылка на установщик проверяется по префиксу), установщик
  сверяется по SHA-256 из API GitHub и лежит в `<data>\updates` с правами каталога данных, поэтому
  обычный пользователь не может подменить файл, который запустит SYSTEM. msiexec запускается вне
  Job Object задания: установщик останавливает саму службу. Новая служба читает `updates\pending.json`
  и записывает итог; окно в трее перезапускается через `WTSQueryUserToken` + `CreateProcessAsUserW`.
* **Перенос**: `export_settings` / `steady export` отдаёт задания, хранилища, подключения,
  уведомления, рабочий каталог, метки планировщика и учётные записи Google Drive. Пароли в файле
  открытым текстом (DPAPI другого компьютера не читается); в журнал пишутся только числа.
  `import_settings` / `steady import-settings` шифрует их заново. Журнал запусков и состояние
  инкремента не переносятся. Копия задания (`copy_job`, правая кнопка в GUI) — новый id и имя
  «(копия)», секреты остаются DPAPI этой машины.
* **Внешние программы**, запускаемые от SYSTEM (1С, 7-Zip, sqlcmd), проверяются
  `acl::check_trusted_exe`: путь абсолютный, файл и каталоги над ним не может изменить никто,
  кроме SYSTEM / Администраторов / TrustedInstaller. PowerShell — полный путь из `%SystemRoot%`.
* **Тайм-ауты.** 1С, sqlcmd, PowerShell и 7-Zip запускаются через Job Object (`process::run`):
  по полю задания `timeout_minutes` (или по умолчанию: 1С 3 ч, SQL 6 ч, файлы и Hyper-V 12 ч)
  дерево процессов завершается, задание — ошибкой. Осиротевшие recovery-точки Hyper-V
  удаляются при тайм-ауте и перед следующим запуском.
* Для проверок рядом с установленной службой: `STEADY_PIPE=<имя> steady --data-dir <каталог> console`.
* Пароль `sqlcmd` — переменная `SQLCMDPASSWORD`. 7-Zip (`-p`) и 1С (`/P`, `/UC`) другого канала не имеют:
  аргумент виден в списке процессов.
* Восстановление файлов: `steady restore` (полная + инкременты, `manifest.deleted`). ВМ — `steady restore-vm`.

Хранение сейчас — JSON-файлы в `%ProgramData%\SteadyBackup` (jobs/, state/, history.jsonl, logs/).
Переход на SQLite — при росте каталога файлов (сотни тысяч файлов в инкрементных заданиях).
