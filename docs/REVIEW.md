# SteadyBackup — разбор кода и очередь задач

Дата разбора: 2026-11-10. Версия: 0.1.0.

**Как сделан разбор.** Прочитан почти весь Rust-код (`steady-core`, `steady-service`), документация,
`tools\*.ps1`, `hyperv.ps1`. Бегло просмотрены `notify.rs`, вторая половина `resources.rs` и GUI.
Не прочитан `hyperv-restore.ps1`. Проект не собирался, тесты и служба не запускались: все выводы
сделаны по чтению кода. Номера строк — на дату разбора; перед правкой сверяй с текущим файлом.

Правила работы агента — в `AGENTS.md` в корне.

## Общая оценка

Рабочий прототип с аккуратной архитектурой: чёткое разделение ядра, службы и GUI; единый трейт
`Target` для всех назначений; атомарная отправка через `.partial`; состояние инкремента фиксируется
только после успешной отправки; секреты маскируются при выдаче в GUI.

До боевого использования нужно закрыть: права на каталог данных (повышение привилегий и чтение
секретов), отсутствие тайм-аутов внешних процессов, ошибку в манифесте удалённых файлов,
отсутствие ротации у части заданий MSSQL. Восстановление реализовано только для Hyper-V.

Объём: ядро ≈ 4100 строк Rust, служба ≈ 1200, GUI ≈ 2900 строк C++. Модульных тестов около десяти
(расписание, разбор имён наборов, WebDAV, DPAPI, фильтр уведомлений).

### P0-1 ◐ Закрыть права на каталог данных

> **2026-11-10, код готов, ждёт установки.** `acl::secure_data_dir` выставляет DACL
> `O:BAD:P(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)` на каталог и всё содержимое (`TREE_SEC_INFO_RESET`,
> владелец — Администраторы); вызывается в `main()` до запуска службы (в т.ч. для `--data-dir`) и в
> `steady install`. Служба загружает задания через `Store::for_service` — файлы с владельцем не
> SYSTEM/Администраторы пропускаются с ошибкой в журнале. Тесты: `acl::tests`, `store::tests`.
> До установки подтверждено: `icacls` на этой машине показывал `Пользователи:(RX)` и `(WD,AD)`.
> После установки проверить приёмку: `icacls`, чтение `jobs\*.json` обычным пользователем,
> что задание PayDesk загружается.

**Где:** права нигде не задаются; каталог создаётся через `create_dir_all`
(`store.rs`, `state.rs`, `resources.rs`, `main.rs::init_logging`), `tools/install.ps1`.

**Проблема.** `%ProgramData%\SteadyBackup` наследует права `ProgramData`: по умолчанию обычные
пользователи могут читать файлы и создавать новые. Следствия:

* пользователь кладёт JSON в `jobs\` с источником `one_c`, своим `platform_exe` и расписанием —
  служба запускает этот файл от SYSTEM (`source/onec.rs`, `Command::new(&exe)`);
* файлы заданий, хранилищ, подключений, токенов Google и настроек уведомлений читаемы, а DPAPI
  используется в области LocalMachine с константной энтропией (`secret.rs:9`, `secret.rs:43`),
  поэтому расшифровать секреты может любой локальный процесс.

Фактические права на конкретной машине нужно подтвердить: `icacls "%ProgramData%\SteadyBackup"`.

**Что сделать.**

1. При старте службы и в `steady install` создавать каталог данных с явным DACL:
   SYSTEM и «Администраторы» — полный доступ, наследование от родителя отключено,
   права распространяются на вложенные объекты. Для уже существующего каталога — переустанавливать
   DACL и владельца (каталог мог быть создан раньше с унаследованными правами).
2. При загрузке задания отклонять файл, владелец которого не SYSTEM и не «Администраторы»
   (защита на случай, если права снова ослабнут).
3. То же для `--data-dir`, заданного вручную в режиме службы.

**Приёмка.** `icacls` показывает только SYSTEM и Администраторов; обычный пользователь не может
прочитать `jobs\*.json` и создать файл в `jobs\`; GUI без прав администратора по-прежнему видит
список заданий и журнал через IPC; после обновления существующие задания читаются.

### P0-2 ◐ Исполняемые файлы из задания и проверка клиента IPC

> **2026-11-10, код готов, ждёт установки.**
> 1. `acl::check_trusted_exe`: путь абсолютный, файл существует; ни файл, ни каталоги над ним не
>    дают прав на изменение никому, кроме SYSTEM / Администраторов / TrustedInstaller (для файла —
>    запись, для его каталога — ещё и добавление файлов, выше — удаление/смена прав; владелец
>    объекта должен быть доверенным). Применяется к `platform_exe`/найденной платформе 1С,
>    7-Zip (`find_7zip`), sqlcmd. На этой машине проходят: 7-Zip (оба), 1cv8.exe 8.5.1.1529,
>    SQLCMD.EXE (ODBC 170), steady.exe в Program Files, powershell.exe; отклоняется steady.exe из
>    каталога сборки. Тесты: `acl::tests`.
> 2. `powershell.exe` — полный путь из `%SystemRoot%` (`util::powershell_exe`);
>    `sqlcmd` — поиск в каталогах SQL Server в Program Files, затем по PATH, с проверкой прав.
> 3. `client_is_admin`: `ImpersonateNamedPipeClient` + `OpenThreadToken` + `CheckTokenMembership`
>    (Администраторы или SYSTEM). PID не используется.
> 4. Решение пользователя (2026-11-10): **неповышенные администраторы управлять не могут** —
>    только просмотр. В GUI кнопка «Изменить настройки…» перезапускает программу через UAC
>    (`--elevated`, отдельный экземпляр).
> Проверено на копии службы (`steady console`, канал `STEADY_PIPE`) из неповышенного процесса:
> `status` → `admin: false`, `list_storages` разрешена, `save_job` и `protect` — «доступ запрещён».
> Повышенный клиент после установки не проверен.

**Где:** `source/onec.rs` (`platform_exe`), `archive.rs::find_7zip`, `ipc.rs:128–166` (`client_is_admin`).

**Проблема.**

* `platform_exe` из задания запускается от SYSTEM без проверок.
* `sqlcmd` и `powershell.exe` ищутся по `PATH`.
* Администратор считается по членству в группе даже в неповышенном токене — это осознанное решение
  (GUI работает без UAC), но вместе с `platform_exe` любой процесс в сеансе администратора получает
  выполнение кода от SYSTEM.
* Проверка идёт по PID клиента (`GetNamedPipeClientProcessId` → `OpenProcess`), что уязвимо
  к повторному использованию PID.

**Что сделать.**

1. Перед запуском `platform_exe` и 7-Zip проверять: путь абсолютный, файл и его каталог недоступны
   для записи никому, кроме SYSTEM / Администраторов / TrustedInstaller.
2. `powershell.exe` и `sqlcmd` запускать по абсолютному пути (`%SystemRoot%\System32\WindowsPowerShell\v1.0\`;
   для `sqlcmd` — найденный полный путь с той же проверкой).
3. Проверку администратора перевести на `ImpersonateNamedPipeClient` + анализ токена потока.
4. Вопрос к пользователю (не решать самостоятельно): оставлять ли управление для неповышенных
   администраторов.

**Приёмка.** Задание с `platform_exe` в каталоге, доступном пользователю на запись, завершается
понятной ошибкой; тесты на функцию проверки пути.

### P1-1 ☑ Тайм-ауты внешних процессов

> **2026-11-10.** `process::run`: Job Object с `KILL_ON_JOB_CLOSE`, по тайм-ауту завершается дерево
> процессов, ошибка называет этап. Поле задания `timeout_minutes` (`#[serde(default)]`; 0 и отсутствие —
> по типу источника: 1С 3 ч, SQL 6 ч, файлы и Hyper-V 12 ч). Подключено к 1С, sqlcmd, 7-Zip (упаковка
> и проверка), PowerShell Hyper-V (экспорт, восстановление, список ВМ в IPC). Осиротевшие
> recovery-точки удаляются перед следующим экспортом и сразу после тайм-аута (`DestroySnapshot`
> с ожиданием задания WMI; имя ВМ — аргумент сценария). В GUI — «Прервать, если длится дольше»
> на странице расписания.
> Проверено: `cargo test --workspace` — 26 тестов, в том числе `timeout_kills_process_tree` (родитель
> и потомок завершены) и разбор старого JSON без поля; `cargo clippy --workspace --all-targets` —
> новых замечаний нет; GUI собран. На реальной ВМ Hyper-V уборка точек не запускалась.
> В установленную службу попадёт вместе с `tools\install.ps1` (сейчас там сборка от 10.11.2026 9:18).

**Где:** `source/onec.rs` (`cmd.status()`), `archive.rs::run`, `source/mssql.rs::sqlcmd`,
`source/hyperv.rs` (оба вызова PowerShell), `ipc.rs` (`ListVms`).

**Проблема.** Ни один внешний процесс не ограничен по времени. Исполнитель один (`engine.rs::worker`),
поэтому зависшая 1С (невидимый диалог в сеансе 0) останавливает все задания навсегда.

**Что сделать.** Общая функция запуска с тайм-аутом и завершением дерева процессов (Job Object с
`KILL_ON_JOB_CLOSE`). Тайм-аут — поле задания с разумным значением по умолчанию по типу источника
(`#[serde(default)]`). По тайм-ауту — ошибка задания с указанием этапа. Для Hyper-V при принудительном
завершении сценария убедиться, что контрольная точка удаляется (сейчас это делает `catch` в сценарии,
который при убийстве процесса не выполнится) — добавить уборку «осиротевших» recovery-точек при
следующем запуске.

**Приёмка.** Тест с процессом-заглушкой, который спит дольше тайм-аута: функция возвращает ошибку,
процесс и его потомки завершены.

### P1-2 ☑ Непрочитанные файлы попадают в `deleted` манифеста

> **2026-11-10.** `deleted` = база − увиденные. Увиденные — файлы текущего каталога, сбойные
> (`failed`, в каталог по-прежнему не заносятся) и всё под префиксами каталогов, которые не удалось
> обойти. Совпадение префикса — только по границе `/`. Предупреждение задания, если каталог пропущен.
> Проверено на временных каталогах: занятый файл (sharing violation) в `failed` и не в `deleted`,
> удалённый — в `deleted`, после разблокировки попадает в следующую инкрементную копию;
> каталог с запретом чтения (`icacls /deny`) не помечает свои файлы удалёнными.
> `cargo test --workspace` — 29 тестов; clippy — новых замечаний нет.

**Где:** `source/files.rs:134–136` (вычисление `deleted`), `Run::fail` (`files.rs:79–83`),
пропуск ошибок обхода (`files.rs:174–179`).

**Проблема.** `deleted` = файлы базового каталога, которых нет в текущем. Файл, который не удалось
прочитать (занят, нет доступа), в текущий каталог не заносится и поэтому числится удалённым.
То же для всех файлов в каталоге, который не удалось обойти. Восстановление по манифесту удалит
существующий файл.

**Что сделать.** Вести множество ключей, увиденных при обходе, включая сбойные; для ошибок обхода
каталога — множество префиксов. `deleted` = база − увиденные − всё под сбойными префиксами.
Сбойные файлы остаются в `failed`.

**Приёмка.** Тесты на временных каталогах: (а) файл из базы заблокирован → он в `failed`, не в `deleted`;
(б) файл действительно удалён → в `deleted`; (в) следующая копия после разблокировки включает файл.

### P1-3 ☑ Ротация для дифференциальных и журнальных заданий MSSQL

> **2026-11-10, вариант А (подтверждён пользователем).** В `Retention` добавлены `keep_days` и
> `keep_sets` (`#[serde(default)]`, 0 = выключено). Старый JSON с одним `keep_full` читается и
> ротируется как раньше. Срок и число удаляют только наборы вне цепочки сохранённой полной
> (журнал и разностные MSSQL, где своих полных нет, и хвост старше самой старой сохранённой полной).
> Цепочку `keep_full` они не ломают. Чужие имена и `.partial` не трогаются. В GUI — поля на странице
> «Хранение копий».
> Проверено: тесты `rotate` на `Target` в памяти (срок, граница срока, число, `keep_full` без изменений,
> цепочка не удаляется по сроку, старый JSON). `cargo test --workspace` — 35 тестов; clippy — новых
> замечаний нет. На реальном SQL Server не запускалось.

**Где:** `pipeline.rs:168–192` (`rotate`), `source/mssql.rs:22–26` (соответствие вида копии).

**Проблема.** Ротация оставляет `keep_full` последних полных копий *с именем этого задания*.
У задания MSSQL вид копии фиксирован; у заданий `differential` и `log` полных копий под своим именем
нет, поэтому `rotate` всегда выходит на `fulls.len() <= keep_full` и ничего не удаляет —
назначение растёт бесконечно.

**Что сделать (согласовать с пользователем вариант).**

* Вариант А: в `Retention` добавить `keep_days` и/или `keep_sets` — удаление наборов без полных копий
  по возрасту/количеству.
* Вариант Б: одно задание MSSQL с расписанием «полная / дифф. / журнал» и общей цепочкой.

Вариант А проще и не меняет формат существующих заданий.

**Приёмка.** Тесты `rotate` на поддельном `Target` в памяти: только инкрементные наборы + `keep_days`
→ старые удалены; существующее поведение `keep_full` не изменилось; чужие файлы не тронуты.

### P1-4 ☑ Разрыв цепочки при частичном сбое назначений

> **2026-11-10, минимальный вариант.** В `JobState` поле `force_full` (`#[serde(default)]`).
> Если инкрементная или дифференциальная копия дошла хотя бы до одного назначения, но не до всех,
> состояние сохраняется с `force_full`, в предупреждении прямо сказано, что следующая копия будет
> полной. Файлы, Hyper-V и MSSQL (журнал и разностная становятся полной) это учитывают. После полной,
> дошедшей до всех назначений, флаг снимается. Старый `state\*.json` без поля читается.
> Полное решение (состояние по каждому назначению и досылка пропущенных наборов) не делалось.
> Проверено: тест двух локальных назначений — второе падает на инкременте, следующая копия полная
> в оба; `cargo test --workspace` — 37 тестов; clippy — новых замечаний нет. На реальном SQL и Hyper-V
> не запускалось.

**Где:** `pipeline.rs:110–117`.

**Проблема.** Состояние сохраняется, если копия дошла хотя бы до одного назначения. В назначении,
куда инкремент не дошёл, цепочка остаётся с дырой, а следующие инкременты строятся уже от нового
состояния. В журнале это только предупреждение.

**Что сделать.** Минимально: при частичном сбое инкрементной/дифференциальной копии помечать в
состоянии «следующая копия — полная» (поле с `#[serde(default)]`) и явно писать это в предупреждение.
Полное решение (состояние по каждому назначению, досылка пропущенных наборов) — отдельная задача,
обсуждать с пользователем.

**Приёмка.** Тест: два назначения, второе падает на инкременте → следующая копия полная в оба.

### P1-5 ☑ Рабочий каталог: место на диске и уборка

> **2026-11-10.** `settings.json`: `work_dir` (пусто — `<data>\work`). Свой путь абсолютный, не корень
> диска и не каталог данных; на него ставятся права P0-1 при сохранении и при старте службы.
> При старте удаляются только каталоги `<uuid>_<32 hex>` — чужие файлы остаются. Перед копированием
> файла известного размера и перед упаковкой — ошибка «недостаточно места в рабочем каталоге».
> IPC `get_settings` (чтение) и `save_settings` (администратор). В GUI — «Рабочий каталог».
> Упаковка 7-Zip без staging не делалась (отдельный шаг в разборе).
> Проверено: тесты очистки, запрета опасных путей и текста ошибки о месте; `cargo test --workspace` —
> 43 теста. На заполненном диске не запускалось.

**Где:** `engine.rs:124`, `main.rs:94` (`work_dir = data_dir\work`), `pipeline.rs:53–56`,
`pipeline.rs:131–136` (`Cleanup`).

**Проблема.**

* Staging и архив лежат на системном диске и одновременно занимают до двух объёмов источника.
  Для ВМ и больших файловых наборов это может заполнить диск C:. Проверки свободного места нет.
* При остановке службы или сбое питания `Cleanup` не выполняется; при старте `work\` не чистится.

**Что сделать.** Параметр рабочего каталога (глобальная настройка службы; для каталога действуют
требования P0-1). Очистка `work\` при старте службы. Проверка свободного места перед подготовкой
источника, где размер известен заранее, и понятная ошибка «недостаточно места в рабочем каталоге».
Дальше (отдельно): для файлов — упаковка 7-Zip по списку без копирования в staging.

**Приёмка.** После аварийного завершения и перезапуска `work\` пуст; тест на очистку.

### P1-6 ☑ Остановка службы во время задания

> **2026-11-10.** `CancelFlag` в `RunContext`. Остановка службы и `cancel_job` (только администратор)
> выставляют его; конвейер проверяет флаг между этапами и файлами, `process::run` завершает дерево
> процессов через Job Object. Журнал: «прервано остановкой службы» или «задание отменено».
> SCM получает `StopPending` и служба ждёт исполнителя до 30 с. В GUI — кнопка «Отменить».
> Проверено: тест отмены спящего процесса (завершился, не дожидаясь тайм-аута). Остановка настоящей
> службы Windows не запускалась.

**Где:** `service.rs::run_until`, `engine.rs::stop`, `engine.rs::worker`.

**Проблема.** `stop()` только выставляет флаг; исполнитель не дожидается, процесс завершается посреди
задания. Отмены задания нет ни из службы, ни из GUI.

### P1-10 ☐ IPC читает строку целиком до проверки размера

## Новое: задание обновления 1С

**2026-11-22 · ☑ код, модульные тесты и сборка; на реальной базе не проверялось.**

Источник `one_c_update` обновляет файловую или серверную базу по цепочке `.cfu`/`.cf`: читает версию,
при наличии плана блокирует новые сеансы через COM, завершает сеансы через `rac` либо только локальные
процессы файловой базы с точным `/F`, сохраняет `.dt` в `backup_dir` через временное имя и `rename`,
выполняет `UpdateCfg`/`UpdateDBCfg` и проверяет версию после каждого шага. Отсутствие новых пакетов —
no-op без `.dt` и отключения сеансов; новая версия без пути из текущей — ошибка. Исходная блокировка
восстанавливается после успеха и ошибок до начала обновления;
при ошибке после начала `UpdateCfg` остаётся включённой. Автоматического отката и ротации `.dt` нет;
назначения, архивирование и `retention` не используются. `run_handlers` по умолчанию `false`.

Секреты хранятся с DPAPI и не пишутся программой в журнал. Передача `/P`, `/UC` и пароля RAC в командной
строке остаётся известным ограничением: аргументы могут быть видны средствами ОС.

**Проверки.** `cargo test --workspace` — 124 теста `steady-core` (4 прежних `#[ignore]` для VSS), 21
интеграционный тест `one_c_update`, 12 тестов `steady-service`, ошибок нет. `cargo clippy --workspace
--all-targets` — без новых замечаний (шесть прежних в `pipeline`, `resources`, `files`, `onec`).
`cmake --build build-gui` — собрано. Покрытие не измерялось: `cargo-llvm-cov` не установлен.

**Что не проверено (нужны живая платформа и база):** реальные COM-блокировка и восстановление исходного
состояния, `rac` на кластере, завершение локальных процессов по `/F`, выгрузка `.dt` и шаги
`UpdateCfg`/`UpdateDBCfg`, обработчики БСП. Нестандартный порт агента RAC не настраивается: для
`сервер:1541` используется `сервер:1540`, другой порт нужно указывать в коде. Абсолютность `backup_dir`
не проверяется. Ротации `.dt` нет — каталог копий растёт.

**Исправление 2026-11-22 после ошибки в файловой базе:** если `unlock_code` не задан, перед установкой
блокировки создаётся временный код. Иначе блокировка с пустым кодом запрещала и проверку сеансов,
и снятие блокировки самим заданием (`Начало сеанса с информационной базой запрещено`). Добавлен
регрессионный тест генерации и сохранения кода. На реальной базе исправление не запускалось.
Следующая ошибка `Предполагается наличие VBArray` исправлена тем же циклом: результат
`ПолучитьСеансыИнформационнойБазы()` — коллекция 1С, поэтому перебор идёт через
`Количество()` и `Получить(i)`, без `VBArray`.

## Новое: загрузка обновлений 1С

**2026-11-22 · ◐ код и модульные тесты; вживую скачивание не проверялось.**

Источник `one_c_download` («Загрузка обновлений 1С», перенос `1c_autoupdate` из `rs1c-build\autoupdate`)
скачивает обновления 1С по учётной записи ИТС в постоянные каталоги задания. Три направления за запуск:
обновления конфигураций через сервис обновлений 1С — цепочка звеньев в
`<template_dir>\<путь из сервиса>\1cv8.zip` с распаковкой при `unzip_files`; архив платформы из того же
сервиса — `<platform_dir>\<версия>.zip`; дистрибутивы последних `count` версий с releases.1c.ru —
`<platform_dir>\<версия>\<файл>`, уже скачанные файлы пропускаются. Учётные записи ИТС выбираются
по имени (`platform`/`releases`/`configurations[].its_account`), пусто или опечатка — первая из списка.
Прокси с Basic-авторизацией, `insecure_tls`, `check_only`. Отдельная ветка конвейера: без staging,
7-Zip, назначений и ротации; общие `attempts` к ней не применяются.

Версия запоминается только после скачивания цепочки целиком или успешной записи архива платформы,
поэтому неудачное звено повторяется следующим запуском. Состояние — отдельный файл
`<data>\state\<id>.download.json` (платформа и версии конфигураций по `program_name`), файл задания
не перезаписывается, обычное состояние инкрементных копий не задействовано. Сбой направления —
ошибка задания с перечнем неудач и числом сохранённых файлов. Новые зависимости ядра: `regex`
(разбор страниц портала), `zip` (распаковка, deflate/deflate64), `native-tls` (TLS через хранилище
сертификатов Windows).

**Проверки.** `cargo test --workspace` — 129 тестов `steady-core` (4 прежних `#[ignore]` для VSS),
24 интеграционных `one_c_download`, 21 `one_c_update`, 12 `steady-service`; ошибок нет.
`cargo clippy --workspace --all-targets` — без новых замечаний (шесть прежних в `pipeline`,
`resources`, `files`, `onec`). `cmake --build build-gui` — собрано.

**Исправлено по ревью до коммита:** пароль прокси уходил в сеть как DPAPI-шифротекст — теперь
расшифровывается при сборке URL, логин и пароль кодируются; восстановлена передача `Authorization`
при том же хосте и добавлено требование https для запросов с учётными данными ИТС; отчёт больше не
показывает пустой набор (при `files == 0` пишется «новых файлов нет»/«проверка без скачивания»,
уведомление — «Обновления 1С: …»); учётная запись `releases` наследуется от «Платформы», как в
оригинале; отмена прерывается как отмена, а не как ошибка скачивания; распаковка идёт через
`<dir>\.unpack-<uuid>` с переносом файлов; пустая цепочка `upgradeSequence` — ошибка, версия не
записывается. Ошибки `SaveJob` в IPC теперь держат задание в `Box`, чтобы вариант запроса не раздувался.

**Что не проверено (нужны действующая учётная запись ИТС и сеть):** реальные запросы к
`update-api.1c.ru`, скачивание и распаковка настоящих `.cfu` и дистрибутивов платформы, работа через
прокси, поведение при отключённой проверке сертификатов. Скачанное не ротируется, каталоги растут,
пока файлы не удалят вручную; одновременная работа двух заданий с одним `template_dir` не проверялась.

### Выбор конфигураций ИТС в окне задания (2026-11-22)
